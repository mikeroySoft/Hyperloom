Optimizing a Model with ROCm™ Hyperloom

Run an autonomous, agentic end-to-end inference optimization of your own model on this workstation — a Radeon AI PRO R9700 (gfx1201, 32 GB) with the rocm-cli TheRock ROCm 7.14 runtime — and read the validated throughput gains it delivers.

§Overview

ROCm Hyperloom is an autonomous agentic system that optimizes end-to-end LLM inference workloads on AMD GPUs. You give it a model, a serving framework, and a workload shape (concurrency, input/output lengths); it measures a baseline, then iteratively proposes, applies, benchmarks, and keeps-or-reverts optimizations — server arguments, environment variables, source patches, and (on Instinct hardware) GPU kernels — until the time budget runs out or the target gain is hit. The whole loop runs unattended and leaves behind a reproducible session directory with a final report and a machine-readable breakdown.

It combines four sub-systems:

ComponentRoleHardware scope
TraceLensProfiling brain — consumes traces, finds bottleneck kernels, derives roofline targetsHardware-agnostic
Magpie + IntelliKitTrace collection, benchmark runners, low-level GPU profilingInstinct MI300X/MI325X/MI355X
GEAKMulti-agent GPU kernel optimizer for hot kernelsInstinct MI300X/MI325X/MI355X
Arbor knowledge baseRecipe store of hardware learnings, pitfalls, and prior campaign artifacts that guides the searchAny
What you'll learn How the Hyperloom optimization loop works · which phases run (and which must be disabled) on an RDNA4 workstation · how to install, configure, launch, monitor, and interpret a full optimization session for your own model.

§How Hyperloom Works

The Coordinator advances a session through a six-phase state machine. On this system the two Instinct-gated phases are disabled (see the reality check below), so the run concentrates on framework-level exploration and workload sweeps:

PRELUDE
baseline→ FRAMEWORK_AGENT→ EXPLORE
args · env · patches→ KERNEL_AGENT→ SWEEP
conc / ISL / OSL→ CLOSE
report
PhaseWhat happensOn this system
PRELUDETarget analysis, baseline throughput measurement, first performance analysis (roofline/profile)Runs (baseline only; roofline disabled — Magpie profiling runners are Instinct-only)
FRAMEWORK_AGENTFramework enablement: discovery, candidate patches, escalation ladder up to compiled buildsDisabled via --no-framework-agent (mirrors the shipped 3h preset)
EXPLORESearches server-argument and environment variants; specialists propose targeted patches; every KEEP is re-benchmarked and end-to-end revalidatedMain value on the R9700
KERNEL_AGENTGEAK kernel optimization, GEMM tuning, operator tuningDisabled via --no-kernel (GEAK targets gfx942/gfx950)
SWEEPConfirms the optimized stack wins across concurrency and sequence-length frontiersRuns
CLOSEFinal report (reports/final.md) and session_breakdown.jsonRuns

All writes flow through a governed intent pipeline: the Orchestration agent proposes, a Critic reviews, an accuracy gate and PolicyGate enforce phase ordering, path sandboxing, and single-writer rules. Every kept change is benchmarked with the bundled InferenceX benchmark_serving.py client via Magpie wrappers; the headline objective is output throughput in tok/s per GPU.

§Support-Matrix Reality Check

Important — unvalidated hardware Hyperloom v1.0.0a1 is validated only on AMD Instinct MI300X / MI325X / MI355X with ROCm 7.2.x (docs/compatibility.rst). The CLI's --gpu-type flag literally accepts only mi300x | mi308x | mi325x | mi355x (cli/parser.py), and the bare-metal installer warns untested (supported: gfx942/gfx950) on any other architecture. Running on the R9700 is an experimental, best-effort path: expect rough edges, and treat any failure in the disabled-phase plumbing as out-of-contract.

Concrete consequences for this workstation, and how this runbook handles each:

ConstraintWhyMitigation in this runbook
Docker mode is outThe validated primussafe/sglang / primussafe/vllm-openai-rocm images ship gfx942/gfx950 kernels, not gfx1201Bare-metal mode on the TheRock gfx1201 runtime
--gpu-type can't name the R9700Closed choices listOmit the flag — the shipped 3h demo skill does the same ("omit for auto-detection")
Kernel phase unusableGEAK / IntelliKit / AgentKernelArena are Instinct-only--no-kernel
Roofline / Magpie profiling unusableMagpie runner scripts and the ROCm profiler hotfix target Instinct; the stack here is ROCm 7.14 nightly, not 7.2.x--no-enable-roofline (with --no-kernel this also skips the TraceLens preflight)
Framework-agent phase skippedCompiled-build escalation (AITER, sgl-kernel) assumes the Instinct stack--no-framework-agent
SGLang ROCm wheels are gfx942-targetedSGLANG_ROCM_EXTRA=rocm720 AMD wheel indexUse vLLM built for gfx1201 as the serving framework

What remains — baseline, the EXPLORE search over server arguments/environment/patches with benchmark-gated keeps, the concurrency/ISL/OSL sweep, and full reporting — is precisely the shipped hyperloom-qwen3-8b-3h preset shape, and is the highest-leverage automation for a single-GPU workstation anyway.

§Step 1 — Preflight

Activate the rocm-cli runtime venv and confirm the GPU is visible and idle. Hyperloom's launch contract requires the GPU to be free of foreign serving processes and under ~500 MiB of allocated VRAM.

# The rocm-cli TheRock runtime is a Python venv — activate it
export ROCM_RUNTIME=/home/mike/ROCm/runtimes/wheel/nightly-wheel-gfx120x-all-7-14-0a20260611
source "$ROCM_RUNTIME/bin/activate"

# GPU visible to ROCm and torch?
rocminfo | grep -E 'gfx|Marketing'
python -c "import torch; print(torch.__version__, torch.cuda.get_device_name(0))"

# GPU idle? (expect ~0 MiB used, no serving PIDs)
amd-smi monitor -g 0 2>/dev/null || rocm-smi --showmeminfo vram

Expected: gfx1201 / "AMD Radeon AI PRO R9700" from rocminfo, and 2.9.1+rocm7.14... AMD Radeon AI PRO R9700 from torch.

Note Do all subsequent steps inside this venv, in the same shell. Hyperloom's installer and CLI must see the ROCm torch; the host Python 3.14 will not work.

§Step 2 — Install Hyperloom

Create a dedicated, empty workspace directory. It becomes both the pip install target and the agent workspace — it will legitimately fill up with package directories.

mkdir -p ~/hyperloom-ws && cd ~/hyperloom-ws

python -m pip install \
  https://github.com/AMD-AGI/Hyperloom/releases/download/v1.0.0a1/hyperloom_inference_optimizer-1.0.0a1-py3-none-any.whl \
  --target .

export REPO_ROOT="$(pwd -P)"
export PYTHONPATH="$REPO_ROOT"
Alternative — source checkout Developers can instead use the local clone at /home/mike/dev/amd/Hyperloom as REPO_ROOT; the workspace is then the repository root and .env is created there. Everything below is identical.

§Step 3 — Run Setup & Configure .env

Hyperloom's orchestration agents are LLM-driven — you need an Anthropic (or gateway) API key. If you work inside Cursor / Claude Code / Codex, open the workspace and run the interactive skill /hyperloom-setup. Headless, create .env directly (never paste real keys into an agent chat):

cat > .env <<'EOF'
ANTHROPIC_API_KEY=<PLEASE_FILL_IN>
ANTHROPIC_BASE_URL=https://api.anthropic.com
CLAUDE_MODEL=claude-opus-4-8
# Writable root for sessions, logs, dependency checkouts, runtime env files
USER_DATA_PATH=/home/mike/hyperloom-ws/session
HYPERLOOM_RUN_MODE=baremetal
EOF

Then run the packaged setup backend (bare-metal scenario). It executes install_baremetal.sh in five phases: base preflight → optional framework install → ROCm hotfix → credentials → runtime env persisted to .env.

# Installs vLLM (isolated venv) as part of setup — see Step 4 for why
python -m hyperloom.inference_optimizer.setup -- --install-framework vllm --yes
Expected warning Phase 1 preflight will log the GPU architecture as untested (supported: gfx942/gfx950) — that is the known-unvalidated R9700 path, not a failure. The ROCm profiler hotfix (phase 3) only applies to eligible 7.2.x stacks and is skipped here; that's fine because roofline/profiling is disabled in Step 5.

§Step 4 — Serving Framework (vLLM for gfx1201)

Hyperloom optimizes a serving framework; it does not replace one. The framework must import and serve your model on this GPU before Hyperloom touches it. The setup step above already installed vLLM the way Hyperloom prescribes: the official ROCm vLLM wheel (wheels.vllm.ai, Python 3.12) pins its own torch, so it goes into a dedicated isolated venv (VLLM_VENV_ROOT, --framework-env isolated — the vLLM default) and never touches the TheRock torch in your runtime venv. ROCm 7.2+ vLLM wheels include RDNA4/gfx1201 support.

# If you skipped it during setup, install manually into an isolated venv:
python -m pip install vllm --extra-index-url https://wheels.vllm.ai/rocm/

# Smoke test: serve your model and hit it once
export MODEL_PATH=/path/to/your/model     # HF-style dir containing config.json
vllm serve "$MODEL_PATH" --max-model-len 4096 &
# wait for "Application startup complete", then:
curl -s localhost:8000/v1/completions -H 'Content-Type: application/json' \
  -d '{"model":"'"$MODEL_PATH"'","prompt":"Hello","max_tokens":8}'
kill %1
Do not proceed until this smoke test passes. If vLLM cannot load and serve the model on the R9700 by itself, Hyperloom cannot optimize it — the FRAMEWORK_AGENT phase that would normally repair enablement gaps is disabled on this hardware. Pick a model that fits: with 32 GB VRAM, bf16 models up to ~14B parameters (or larger with quantized weights) leave adequate KV-cache headroom.

Record the framework in .env so demo skills and the CLI inherit it:

echo 'FRAMEWORK=vllm' >> .env

§Step 5 — Launch the Optimization

First run the runtime installer (installs the optimizer package extras, Magpie benchmark wrappers, and the InferenceX benchmark client) and source the generated env file — required even for no-kernel runs:

bash "$REPO_ROOT/hyperloom/inference_optimizer/assets/install.sh" --skip-kernel-agent
source "$USER_DATA_PATH/runtime/kernel-agent.env.sh"
Note With a source checkout the path is $REPO_ROOT/src/hyperloom/inference_optimizer/assets/install.sh. --skip-kernel-agent skips cloning the Instinct-only kernel tooling (GEAK etc.); the run-level switch is separately --no-kernel below.

Now launch. This is the 3h-preset shape adapted to the R9700 — kernel, framework-agent, and roofline lanes off; EXPLORE and SWEEP on; 64-way concurrency at 1024/1024 tokens, bf16:

export LAUNCH_INFO_FILE="$USER_DATA_PATH/launch-info.json"
export RUN_LOG="$USER_DATA_PATH/optimizer-run.log"

setsid nohup python3 -m hyperloom.inference_optimizer.cli --verbose optimize \
  --model "$MODEL_PATH" \
  --framework vllm \
  --tp 1 --ep 1 \
  --conc 64 --isl 1024 --osl 1024 \
  --precision bf16 \
  --target-gain 30 \
  --max-hours 3 \
  --no-kernel \
  --no-framework-agent \
  --no-enable-roofline \
  --tick-interval-sec 30 \
  --launch-info-file "$LAUNCH_INFO_FILE" \
  > "$RUN_LOG" 2>&1 < /dev/null &

After ~30 seconds, verify health exactly the way the shipped skills do:

sleep 30
REAL_PID=$(jq -r .pid "$LAUNCH_INFO_FILE")
SESSION_DIR=$(jq -r .session_dir "$LAUNCH_INFO_FILE")
test -d "/proc/$REAL_PID"            && echo "process alive"
test -f "$SESSION_DIR/manifest.json" && echo "manifest ok"
test -f "$SESSION_DIR/state.json"    && echo "state ok"
jq -r '.stop_reason // "running"' "$SESSION_DIR/state.json"
Session layout Sessions live at $USER_DATA_PATH/<model_basename>/<UTC_timestamp>/ containing manifest.json, state.json, storage/coordinator.db, runs/{baseline,explore,sweep,…}/<task_id>, and reports/. Always resolve the session dir from the launch-info JSON — never by "latest timestamp".

Sizing the workload for 32 GB VRAM

KnobGuidance on the R9700
--tpAlways 1 — single GPU.
--concSet to your real target concurrency. 64 is a solid default; the SWEEP phase separately measures the ladder 256,128,64,32,16,8,4,2.
--isl / --oslMatch production. Bigger values → bigger KV cache; at 1024/1024 with a ~8B bf16 model (~16 GB weights) the remaining ~14 GB of KV cache is comfortable. For 13–14B models, reduce concurrency or lengths.
--precisionbf16. (FP8 presets target Instinct FP8 paths; unverified on RDNA4.)
--max-hours3 for a first end-to-end check; raise to 8–12 once the pipeline is proven. SWEEP can re-loop into another EXPLORE cycle while budget remains.
--target-gainStop early once the validated cumulative gain (%) over baseline is reached. 30 is the preset default; alternatives: --target-tput (tok/s/GPU) or --target-baseline-dir.

§Step 6 — Monitor

Poll state.json about every 300 seconds — no more often, per the skill contract:

watch -n 300 "jq '{phase, stop_reason, baseline_tput, cumulative_gain,
  current_best: .current_best, last_sweep: .last_sweep}' $SESSION_DIR/state.json \
  && tail -n 5 $RUN_LOG"
FieldMeaning
phaseCurrent pipeline phase (PRELUDE → EXPLORE → SWEEP → CLOSE here)
stop_reasonnull/absent while running; set on completion, budget exhaustion, target hit, or abort
baseline_tputBaseline output throughput measured in PRELUDE (tok/s)
current_bestBest kept configuration: {action, tput, accuracy}
cumulative_gainValidated % gain over baseline — re-measured end-to-end after every KEEP, not a sum of deltas
explore_search.last_roundLatest explore variant decision

Resume an interrupted session (crash, reboot, Ctrl-C) — do not start a new one:

python3 -m hyperloom.inference_optimizer.cli optimize --resume \
  --launch-info-file "$LAUNCH_INFO_FILE"
# Model/workload are read from the saved manifest — do not pass --model

§Step 7 — Read the Results

On CLOSE, Hyperloom writes the operator report to $SESSION_DIR/reports/final.md (and final.json) plus the machine-readable $SESSION_DIR/session_breakdown.json. Three fields to read first:

jq '{tput: .final.throughput_tok_s_per_gpu,
     gain: .final.cumulative_gain_pct_validated,
     path: .final.action_path}' "$SESSION_DIR/session_breakdown.json"
FieldWhat it tells you
final.throughput_tok_s_per_gpuValidated end-of-session serving throughput — the headline number
final.cumulative_gain_pct_validatedValidated gain over baseline
final.action_pathOrdered list of kept changes (server args, env vars, patches) that make up the optimized stack — this is your reproducible recipe
Applying the wins The action_path entries map directly to vLLM server arguments and environment variables. Bake them into your production launch command; each entry's benchmark evidence lives under $SESSION_DIR/runs/explore/….

§Troubleshooting

SymptomCause / fix
argparse: invalid choice for --gpu-typeYou passed an RDNA name. Omit the flag entirely.
Preflight logs untested (supported: gfx942/gfx950)Expected on gfx1201 — informational, not fatal.
Launch aborts on GPU-busy checkAnother process holds >~500 MiB VRAM. Stop stray vLLM/desktop compute jobs; re-check with amd-smi.
ImportError: libamdhip64.so / libhipblas.soMixed ROCm userspaces. Everything must run inside the rocm-cli runtime venv; don't point ROCM_PATH/LD_LIBRARY_PATH at another install.
vLLM OOM during baselineModel + KV cache exceed 32 GB. Lower --conc, --isl/--osl, --max-model-len, or pick a smaller/quantized model.
Run dies with a TraceLens/Magpie profiling errorA profiling lane slipped through — confirm all three of --no-kernel --no-framework-agent --no-enable-roofline are on the command line.
Session seems stuckCheck tail -f $RUN_LOG and state.json.phase. Benchmarks at conc 64 legitimately take minutes. If the process died non-terminally, resume with --resume.
